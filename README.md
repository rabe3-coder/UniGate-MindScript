# UniGate — Mind Script eng.rabe3

## الإصدار: حسابات طلاب ديناميكية + موظفو شؤون محددون مسبقًا

نموذج محلي يعمل بـ **Python + SQLite + HTML/CSS/JavaScript**. الحسابات الجديدة والتسجيلات المؤكدة والمسودات والمواعيد والانتظار مرتبطة بمستخدم منفصل في قاعدة البيانات. **ليس نظام إنتاجي لهويات طلاب حقيقيين**.

## خطوات التشغيل للمرة الأولى على Windows 10

1. ثبّت **Python 3.10 أو أحدث**، مع تفعيل خيار **Add Python to PATH** أثناء التثبيت.
2. فك ضغط الملف `UniGate_eng.rabe3_Deploy_Ready.zip` في مجلد عادي (ليس داخل مجلد مضغوط).
3. لتعيين المدير وثلاثة موظفي شؤون، شغّل `SETUP_STAFF_WINDOWS.bat` **مرة واحدة مبدئيًا**؛ سيطلب منك بالتتابع:
   - اسم دخول واسم ظاهر وكلمة مرور **للمدير الواحد**.
   - اسم دخول واسم ظاهر وكلمة مرور **لكل واحد من ثلاثة موظفي شؤون الطلاب**.
   - اكتب `CONFIRM` لاعتماد البيانات. الكلمات لا تظهر أثناء كتابتها ولا تُحفظ كنص صريح.
4. شغّل `START_WINDOWS.bat`.
5. افتح العنوان `http://127.0.0.1:8765`.
6. الطالب: **إنشاء حساب طالب** → الاسم الكامل → الرقم الجامعي → كلمة المرور → تأكيدها. يصبح الرقم الجامعي اسم الدخول، ويدخل تلقائيًا بعد التسجيل.
7. في المرات التالية: **تسجيل الدخول** فقط بالرقم الجامعي وكلمة المرور. المدير والموظفون يسجلون الدخول ببياناتهم الخاصة، **ولا يستطيعون إنشاء حساب إداري من الموقع**.

### إذا كنت تُحدّث نسختك السابقة وتريد الإبقاء على الطلاب المسجلين

1. أوقف الخادم، وأغلق DB Browser for SQLite.
2. **انسخ `registration.sqlite3` في مكان آمن** قبل أي تحديث.
3. فك ضغط `UniGate_eng.rabe3_Deployment_Patch.zip`، ثم انسخ محتوياته فوق ملفات مشروعك الحالي مع الموافقة على استبدال الملفات **ما عدا قاعدة البيانات** (الحزمة لا تحتوي قاعدة بيانات أصلًا).
4. شغّل `SETUP_STAFF_WINDOWS.bat` لإعادة تعيين بيانات دخول المدير وإنشاء الموظفين الثلاثة. **الحسابات الإدارية القديمة المعروفة بكلمة مرور Demo123! تُعطَّل عند الترقية.** يحتفظ الحساب القديم بمعرّفه وسجل عملياته عند إعادة استخدامه؛ لا يُحذف سجل الطلاب.
5. شغّل `START_WINDOWS.bat`، وادخل ببياناتك الجديدة.

> تنبيه: حسابات الطلاب التجريبية القديمة التي كانت تستخدم كلمة المرور المشتركة `Demo123!` تبقى في قاعدة بياناتك القديمة حفاظًا على سجلاتها، لكنها **غير آمنة لفتح الموقع للعامة**. يجب تغيير كلمات مرورها باستخدام `python change_student_password.py` أو استبدالها بهويات موثّقة قبل أي نشر. قاعدة النسخة الكاملة النظيفة **لا تحتوي حسابات جاهزة** إطلاقًا.

## كيف تغيّر الحسابات المخصصة؟

- إعادة تعيين المدير وثلاثة موظفي الشؤون: `python manage_staff.py setup` أو تشغيل `SETUP_STAFF_WINDOWS.bat` مجددًا.
- لأن المشروع يحتفظ بأدوار رئيس القسم والمالية، لكن لا ينشئ حساباتهما من الويب، يمكنك تعيين بياناتهم محليًا عند الحاجة:
  - `python manage_staff.py set-role --role head`
  - `python manage_staff.py set-role --role finance`
- تغيير كلمة مرور طالب قديم محليًا: `python change_student_password.py`.
- **لا تضع أسماء دخول وكلمات مرور ثابتة داخل HTML أو JavaScript أو GitLab.**

## هل خيارات الطالب محفوظة؟

نعم: التسجيلات النهائية (`enrollments`)، والطلبات في الانتظار (`waitlist`)، والدفع التجريبي (`payments`)، والخطة والعلامات (`student_plan` و`course_grades`)، وكذلك سلة المقررات غير المؤكدة (`student_basket`) مرتبطة بـ `user_id` وتُحفظ داخل SQLite. السلة لا تحجز مقعدًا؛ عند الضغط على «تأكيد التسجيل» يعاد فحص كل الشروط. عند تسجيل الدخول بجهاز آخر **إلى الخادم نفسه وقاعدة البيانات نفسها** تظهر الخيارات المحفوظة. أما نقل مجلد قاعدة البيانات أو تشغيل قواعد منفصلة فينتج بيئات منفصلة.

## سياسة الصلاحيات

| العملية | الزائر | الطالب | شؤون الطلاب | المدير |
|---|---:|---:|---:|---:|
| إنشاء حساب طالب لنفسه | نعم | بعد الخروج | بعد الخروج | بعد الخروج |
| إنشاء حساب بصفة admin أو affairs | لا | لا | لا | لا من الويب |
| رؤية/تعديل بيانات الطالب | لا | بياناته التشغيلية | نعم | نعم |
| إدارة السياسات | لا | لا | لا | نعم |
| تعيين/تغيير كلمات الموظفين | لا | لا | لا من الويب | من كونسول الجهاز فقط |

حتى لو عدَّل الزائر حقل `role` في طلب إنشاء الحساب، يحدد الخادم الدور `student` بشكل ثابت ولا يثق بهذا الحقل.

## الملفات الأساسية

- `app/application/auth.py`: إنشاء الحساب والتحقق وتوليد الجلسات.
- `app/application/basket.py`: إدارة مسودات السلة في SQLite.
- `app/core/security.py`: فحص الجلسات والصلاحيات وتعطيل المستخدمين.
- `app/infrastructure/database.py`: تعريف الجداول وترقية قواعد SQLite الحالية دون إزالة الطلاب.
- `app/api/router.py`: ربط مسارات HTTP بالعمليات.
- `static/js/layout.js`: واجهتا الدخول وإنشاء الحساب، بالعربية والإنجليزية.
- `static/js/actions.js`: إرسال النماذج والتفاعل وحفظ السلة.
- `manage_staff.py`: تخصيص حساب المدير وثلاثة موظفي الشؤون من جهاز المشروع، وليس من API عام.
- `test_accounts.py`: اختبار دورة الحساب والتخزين والأدوار وترحيل القاعدة.
- `docs/AUTH_AND_ACCOUNTS.md`: تصميم الصلاحيات وحدود الأمان.

## الاختبارات

شغّل `python test_accounts.py` لاختبار الحسابات والحفظ على قواعد معزولة. وللاختبارات السابقة، شغّل `python run_tests.py`؛ يولّد حسابات الاختبار فقط داخل قواعد SQLite مؤقتة. **لا تستخدم** متغير `MINDSCRIPT_TEST_DEMO=1` مع قاعدة الطلاب الحقيقية؛ إنه مخصص حصريًا للاختبارات.

## حدود النسخة

- في التسجيل الذاتي، النظام لا يستطيع التأكد أن الشخص يملك الرقم الجامعي فعلًا. **الهوية تحتاج تحققًا جامعيًا** (رمز دعوة/تفعيل إلى بريد رسمي/نظام SSO) قبل استعماله في جامعة فعلية.
- الخادم الحالي يعمل على `127.0.0.1`، وليس مستضيفًا عامًا متعدد الأجهزة. للوصول من أجهزة أخرى يلزم نشر آمن بخادم موحد وHTTPS وجدار حماية وإجراءات أمنية إضافية.
- تسجيل الدخول يستخدم ملفات تعريف ارتباط HttpOnly/SameSite مع صلاحية 12 ساعة وكلمات مرور PBKDF2. تحديد معدل محاولات الدخول موجود بصورة محلية داخل الذاكرة فقط؛ الإنتاج يحتاج خدمة حماية مركزية وقواعد بيانات إنتاجية واختبارات أمنية وحمل.
- الدفع تجريبي، وتعديلات العميل الأخرى جزء من نظام التصميم وليست تأكيدًا لجميع متطلبات التنفيذ الإنتاجي.
- **زر حذف قاعدة البيانات من لوحة الإدارة مُعطّل عمدًا** لحماية الطلاب الحقيقيين. استخدم نسخًا احتياطية وتغييرات قاعدة منظمة بدل التصفير.

## إضافات تجهيز الاستضافة العامة (2026-10-24)

لتجهيز النشر المجاني دون ترحيل SQLite إلى PostgreSQL، أُضيف `app/wsgi.py` ومدخل `deploy/pythonanywhere_wsgi.py` لخطة PythonAnywhere Free. **التشغيل على Windows باقٍ كما هو** عبر `START_WINDOWS.bat` و`server.py`.

- اقرأ `docs/DEPLOY_PYTHONANYWHERE.md` للخطوات التفصيلية من GitHub إلى الرابط العام، واستيراد قاعدة جهازك بصورة خاصة، وإدارة موظفي الشؤون.
- اقرأ `docs/HOSTING_COMPARISON.md` لقيود الاستضافة المجانية ومتى يستحق التفكير بقاعدة Neon PostgreSQL.
- اقرأ `docs/SECURITY_DEPLOYMENT_REVIEW.md` للمخاطر المعروفة.
- اقرأ `docs/TEST_DEPLOYMENT_REPORT.md` لنتائج الاختبارات الفعلية وما لم يُختبر بعد.
- اقرأ `docs/SCHEMA_INVENTORY.md` للجداول والعلاقات والفهارس والمشغّلات.
- اقرأ `docs/API_ENDPOINTS.md` لقائمة API الحقيقية من الشيفرة.
- `python test_deployment_wsgi.py` يشغّل اختبار المدخل العام دون التأثير على قاعدة المشروع.
- `python backup_database.py backup` يصدر نسخة SQLite متسقة؛ لا ترفع نسخ قواعد المستخدمين إلى GitHub.

**تحذير:** حزمة النشر النظيفة لا تحتوي ملف `registration.sqlite3` أو بيانات اعتماد حقيقية. إذا عندك تعديلات على حسابات الطلاب أو الموظفين، انقل قاعدة بياناتك بشكل خاص إلى حساب PythonAnywhere باتباع الدليل، ولا تستخدم GitHub أو موقعًا عامًا كوسيط لقاعدة البيانات.
